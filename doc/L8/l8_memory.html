阶段 4 上下文工程与记忆 · L8 —— 上下文工程第一课

Agent 长期记忆

L1~L7 + 阶段 3 之后，我们的 agent 已经会调工具、会检索知识库、会说 MCP、能在多 worker 下守互斥—— 但它仍然是一条金鱼：每个会话独立装载，关掉这个会话，你昨天告诉它的一切都随轨迹沉入数据库，再也不会被想起。 本课给它装上跨会话的长期记忆，顺带补上项目一直缺的一块拼图：system prompt。

01本课目标

  • 理解 Agent 记忆系统的三个设计问题：记什么、何时记、何时用——每个问题都有至少两条路，本课走一遍并说清取舍
  • 动手：memories 表（Alembic 迁移）→ 提取式写入（LLM JSON → TypedDict 合同）→ system 注入 → remember/forget 工具
  • 补课：role: "system" 消息的语义——项目从 L1 到今天还没有一条 system 消息
  • 验证：今天教它「回答要简短」，明天开一个全新会话问问题，它记得
类型课点（本课的重点之一） LLM 的自由文本输出是整个系统里最不可信的边界——比 HTTP 响应还不可信。本课给出 Any 边界收窄的第三种模式： 防御式解析（isinstance 逐层判断 + TypedDict 合同 + 失败返回空而不炸主流程）。 写代码前每段都过过类型脑内检查，不给 Pylance 留红线。

02背景回顾：为什么说现在的 bot 是金鱼

先复习我们的对话链路（阶段 3 之后的形态，三段式连接管理）：

POST /chat/agent/stream
  ① body 阶段短会话:  建会话 → claim(409 前置)
  ② 装载短会话:       存 user 消息 → 读全量轨迹 → trim_history → build_llm_messages
  ③ LLM 段(零 DB 连接): run_agent_stream 循环(模型↔工具, 秒级 await)
  ④ 收敛短会话:       轨迹单事务写入 → release

这条链路里有两个「金鱼证据」：

证据一：完整 prompt 里没有任何跨会话的信息

模型的完整输入 = build_llm_messages(trim_history(历史))。 历史从哪来？get_conversation_messages——只查当前会话。 哪怕数据库里躺着 100 个会话、几千条消息，模型这轮能看到的也只有本会话的轨迹。

证据二：项目至今没有 system 消息

看 build_llm_messages 的还原逻辑，只认三种角色：

# app/services/agent.py —— 现状
for m in history:
    if m["role"] == "user": ...
    elif m["role"] == "tool": ...
    elif m["tool_calls"]: ...   # assistant + 工具申请单

OpenAI 兼容协议其实支持第四种角色 system——它是给模型的「常设指令」： 人格、规矩、背景知识，不属于任何一轮对话，而是悬在整场对话头上的说明书。 我们从 L1 起就没用它，所以模型的「性格」完全由历史轨迹隐式决定——这正是记忆没有容身之处的原因： 没有 system 这个架子，就算有记忆也不知道往哪挂。

金鱼实验（动手确认现状，1 分钟）

# 会话 1:教它一个偏好
curl -N -X POST localhost:8000/chat/agent \
  -H 'Content-Type: application/json' \
  -d '{"message": "记住:以后所有回答都用简短的列表形式"}'

# 新会话(不传 conversation_id):它还记得吗?
curl -N -X POST localhost:8000/chat/agent \
  -H 'Content-Type: application/json' \
  -d '{"message": "用一句话介绍什么是 Docker volume"}'

第二个请求大概率给你一段流畅的散文体——第一会话里的偏好没有随行。 唯一能「记」的方式是你手动把它写进每轮消息里，这显然不可持续。

03原理：记忆系统的三个设计问题

「给 agent 加记忆」不是一句话的事，它拆成三个独立的设计决策。 每个决策都有两条主流路线，本课的动手部分会各取其一，另一条留作进阶伏笔。

问题一：记什么？

类型例子特点
偏好型「回答要简短」「用中文」「喜欢列表」影响怎么答，最高频
事实型「用户叫小周」「在学 Agent 开发」影响答什么，稳定
事件型「上周三部署失败过一次」带时间线，最复杂，本课不碰

本课收窄为：一句话事实——每条记忆是一行自包含的中文文本， 存进 memories 表。自包含是硬要求： 「它喜欢简短」离开对话现场没有主语，「用户喜欢简短回答」才是合格的一条记忆。

问题二：何时记？

路线机制优点缺点
工具显式给模型注册 remember 工具，模型在对话中主动调用模型自己判断「这句值得记」，精准靠模型自觉，漏记率高；对话被工具调用打断
会话后提取每轮结束后，用一个独立的 LLM 调用扫描「用户说了什么」，产出记忆 JSON稳定可靠，对主对话零打扰——ChatGPT 的 Memory 就是这条路每轮多一次 LLM 调用（成本+延迟）

本课：提取式为主、工具为辅，两条都做——不是因为贪多，而是两条路的代码落点完全不同 （提取在服务层，工具在注册表），正好各教一课的东西，也方便你在验证实验里对比两者的手感。

问题三：何时用？

路线机制适用
全量注入把所有记忆拼成文本，塞进 system prompt记忆少（几十条以内）时最优：实现简单、每条都可见
检索式注入用当前问题做向量检索，只注入相关的 top-k 条记忆多了必须——这正是 L6 pgvector 的用武之地，本课埋伏笔

本课：全量注入。记忆还很少时，检索式是过度设计；但第 05 节的思考题会让你算一算全量注入的 token 账单， 算完你就知道它为什么活不了太久。

补课：system 消息的三条铁律

完整 prompt 的结构（本课之后）:

[ system ]  ← 常设指令:人格 + 长期记忆,永远第一条,每轮都发
[ user    ]  ← 历史...
[ assistant ]
[ tool    ]
[ assistant ]
[ user    ]  ← 本轮新消息
  1. 永远第一条——模型按位置理解指令层级，system 在最前权重最高。
  2. 不进历史、不进 trim——它不是对话的一部分，不存 messages 表，不随轮次增长，滑动窗口裁不到它。
  3. 每轮重新组装——system 是「本轮 prompt 的固定头」，由服务端每次装载时现拼。这和记忆的注入方式严丝合缝：记忆变了，下一轮的 system 自然就变了。

目标架构

                     ┌──────────────────────────────────────────┐
                     │              每轮请求的生命周期            │
                     │                                          │
   装载时(读):       │  memories 表 ──全量读──▶ 拼 system prompt │
                     │                             │            │
                     │                    system + 历史 = prompt │
                     │                                          │
   对话中(写,显式):   │  模型说"记住X" ──▶ remember 工具 ──▶ 写库  │
                     │                                          │
   收敛时(写,提取):   │  轨迹收敛后 ──▶ LLM 提取 ──▶ 新记忆 ──▶ 写库│
                     └──────────────────────────────────────────┘

模型：memories 表

from sqlalchemy import Text
from sqlalchemy.orm import Mapped, mapped_column

from app.database.pgsql_client import Base


class Memory(Base):
    __tablename__ = "memories"

    id: Mapped[int] = mapped_column(primary_key=True)
    # 一句话事实,自包含,如:"用户喜欢简短的列表式回答"
    content: Mapped[str] = mapped_column(Text, comment="长期记忆:一句话事实")

crud 层：crud/memories.py

新建 app/crud/memories.py，签名风格对齐 crud/chats.py （收 AsyncSession、commit 在 crud 内、事务边界=语义单元）：

from sqlalchemy import delete, select
from sqlalchemy.ext.asyncio import AsyncSession

from app.models import memories


async def get_all_memories(db: AsyncSession):
    """全量记忆,按 id 升序(时间线顺序)。"""
    rows = await db.scalars(select(memories.Memory).order_by(memories.Memory.id))
    return list(rows)


async def add_memories(db: AsyncSession, contents: list[str]) -> None:
    """一批记忆一个事务。空列表直接返回——不空跑 commit。

    对齐 chats.append_messages(复数)的哲学:写入的语义单元是"这一轮的
    提取结果",而不是"某一条记忆"。
    """
    if not contents:
        return
    db.add_all(memories.Memory(content=c) for c in contents)
    await db.commit()


async def delete_memory_by_content(db: AsyncSession, content: str):
    """按内容精确匹配删除。返回删除行数(0 = 没找到)。"""
    result = await db.execute(delete(memories.Memory).where(memories.Memory.content == content))
    await db.commit()
    return result.rowcount
为什么返回类型不标、参数却标得一丝不苟？ 项目拍板的哲学：「能推导则不写」。get_all_memories 的返回 （list[Memory]）从 list(rows) 一眼可推，标了是噪音； 而 db: AsyncSession、contents: list[str] 推不出来， 不标 = 隐式 Any 失明。-> None 是唯一例外：对「无返回值」的声明本身有防手滑价值 （谁往里 return 个东西立刻报错），所以保留。

提取层：services/memory.py（本课重头）

新建 app/services/memory.py。它只依赖 llm_client， 不碰 DB（写库是调用方的事），也不碰 openai 类型——边界约定不变。

"""记忆层:跨会话长期记忆的提取与注入。

职责只有两件事:
- extract_new_memories: 收敛后从一轮对话中提取值得记住的新事实(LLM 调用,零 DB)
- build_system_prompt:  装载时把记忆拼进 system prompt(纯函数,零 DB/零 LLM)

读记忆、写记忆是 crud 的事;什么时候提取、什么时候注入,是路由的事。
"""

import json
from typing import TypedDict, cast

from app.services.llm.client import llm_client


# ---- LLM 输出合同:要求模型严格返回 {"memories": ["...", ...]} ----
class MemoryExtract(TypedDict):
    memories: list[str]


# ---- 注入侧:基础人格 + 记忆段 ----
BASE_SYSTEM_PROMPT = "你是 study-fastapi 项目的助手,回答使用中文。"

# ---- 提取侧提示词:只写"判定标准",现有记忆和对话在调用时拼接 ----
EXTRACT_PROMPT = """你是记忆管理员。下面给你一轮对话和现有记忆清单,
判断这轮对话里是否出现了值得长期记住的、关于用户的新信息。

判定标准:
- 只记稳定信息:回答风格偏好、称呼、正在学习/从事的方向、长期约束
- 不记一次性任务细节("帮我写个查询"不算)
- 每条记忆必须自包含:脱离这轮对话也能看懂,以"用户"开头
- 与现有记忆意思重复的不要输出
- 没有值得记的,输出空数组

只输出 JSON,格式严格如下,不要输出任何其他文字:
{"memories": ["用户喜欢简短的列表式回答"]}
"""


async def extract_new_memories(user_text: str, assistant_text: str, existing: list[str]):
    """从一轮对话中提取新记忆。返回新记忆文本列表,空列表 = 本轮没什么可记。

    注意:本函数只做 LLM 调用和解析,不碰 DB——调用方(路由)在收敛块里
    拿着返回值自己写库。秒级 await 之外没有 session,连接纪律天然满足。
    """
    # token 预算意识:超长回复截断,提取只需要"这轮说了什么",不需要全文
    prompt = (
        EXTRACT_PROMPT
        + "\n现有记忆:\n" + ("\n".join("- " + m for m in existing) or "(暂无)")
        + "\n\n本轮对话:\n用户:" + user_text[:2000]
        + "\n助手:" + assistant_text[:2000]
    )
    raw = await llm_client.chat([{"role": "user", "content": prompt}])
    return _parse_memory_extract(raw)


def _parse_memory_extract(raw: str):
    """LLM 自由文本 → MemoryExtract 合同。

    这是 Any 边界收窄的第三种模式(防御式解析):
    - 协议层(L7): isinstance + cast 到 TypedDict 合同
    - 数据层(L6): pydantic 建形状
    - 本处(LLM 输出): 最不可信的输入——模型可能输出废话、截断的 JSON、
      单引号、markdown 代码围栏。逐层 isinstance 防御,
      任何一层不合规就返回 [](失败 ≠ 抛异常,提取失败不该炸掉对话主流程)。
    """
    try:
        data = json.loads(raw)
    except json.JSONDecodeError:
        return []
    if not isinstance(data, dict):
        return []
    data = cast(dict[str, object], data)
    items = data.get("memories")          # .get() 不裸下标——合同键可能被模型省略
    if not isinstance(items, list):
        return []
    # 逐条验形:非字符串/空串剔除。到这里返回值才真正是 list[str]
    return [item for item in items if isinstance(item, str) and item.strip()]


def build_system_prompt(memories: list[str]) -> str:
    """记忆 → system prompt。纯函数,装载时由路由调用。"""
    if not memories:
        return BASE_SYSTEM_PROMPT
    joined = "\n".join("- " + m for m in memories)
    return (
        BASE_SYSTEM_PROMPT
        + "\n\n## 关于用户的长期记忆(回答时遵守)\n" + joined
    )
重点讲解：为什么解析失败返回空而不是抛异常？ 回忆 tools.py 的既定哲学——error-as-data：工具失败返回 error JSON，不抛异常打断 agent loop。 记忆提取是同一个思想，但立场更极端：记忆是锦上添花，主对话是雪中送炭。 提取失败的最坏后果是「这一轮没记住」，而主对话为此 500 是本末倒置。 所以这里的降级方向是「静默缩水」——返回空列表，调用方继续走。05 节思考题第 3 问会追问这个决策的边界。
为什么拼接用 + 而不用 str.format()？ 提示词里有字面花括号 {"memories": [...]}——JSON 示例。 走 .format() 就得把它写成 {{"memories"}} 双花括号转义， 这是个经典手滑陷阱（忘了转义 → KeyError: 'memories'，而且报错位置离病灶很远）。 字符串拼接虽然土，但字面量保持原样，改提示词时不易翻车。

注入侧：build_llm_messages 挂上 system

app/services/agent.py 的 build_llm_messages 加一个可选参数 （默认 None 向后兼容——不传的调用点行为不变）：

def build_llm_messages(history: list[MessageDict], system_prompt: str | None = None):
    """存储格式 → SDK 消息。system(可选) + user/assistant/tool 三种角色逐条还原。"""
    llm_messages: list[ChatCompletionMessageParam] = []

    # system 永远第一:它是本轮 prompt 的固定头,不属于历史,不参与 trim
    if system_prompt is not None:
        llm_messages.append({"role": "system", "content": system_prompt})

    for m in history:
        ...  # 下面原样不动
为什么不做成「把 system 存进 messages 表」？ 存库意味着它会出现在 get_conversation_messages 的结果里、被 trim_history 裁剪、 在每个新会话里重复累积。system 的语义是「每轮现拼的常设指令」——记忆更新了，下一轮的 system 自动就是新的；存库反而把它冻结成了某轮的历史快照。派生数据不落库，和 L3 的 「数据库是对话唯一真相源」不矛盾：记忆的真相源是 memories 表，system 只是它每轮的投影。

工具路径：remember / forget

app/services/tools.py 加两个工具函数（放在 _search_knowledge_base 后面， 风格对齐——短 session、error-as-data）：

from app.crud import memories   # 顶部 import 区


async def _remember(args: dict[str, object]):
    content = args["content"]  # 必填参数已由 execute_tool 按 schema 校验过
    if not isinstance(content, str) or not content.strip():
        return json.dumps({"error": "content 必须是非空字符串"}, ensure_ascii=False)

    async with AsyncSessionLocal() as db:   # 工具内短 session,先例同 _search_knowledge_base
        await memories.add_memories(db, [content.strip()])
    return json.dumps({"result": "已记住: " + content.strip()}, ensure_ascii=False)


async def _forget(args: dict[str, object]):
    content = args["content"]
    if not isinstance(content, str) or not content.strip():
        return json.dumps({"error": "content 必须是非空字符串"}, ensure_ascii=False)

    async with AsyncSessionLocal() as db:
        deleted = await memories.delete_memory_by_content(db, content.strip())
    if deleted == 0:
        return json.dumps({"result": "没有找到完全匹配的记忆,原样告诉模型即可"}, ensure_ascii=False)
    return json.dumps({"result": "已忘掉"}, ensure_ascii=False)

工具描述里的「自包含」要求和提取提示词里的，是同一条合同 两条写入路径（提取 / 工具）产出的记忆会混在一张表里、一起被注入。 形状合同（一句话、以「用户」开头、自包含）必须两处一致——这就是「同一形状的合同， 所有写入侧共同遵守」，和 StoredToolCall 三形合一是同一个纪律，只是这次合同的对象是自然语言。

路由接入：/agent 全量改造（完整版，防漏行）

先加 import（app/routers/chats.py 顶部）：

路由接入：/agent/stream（同款思路，完整版）

流式版有一个额外细节：提取需要最终回复全文，而 run_agent_stream 把文本切碎在事件流里——所以路由在转发事件时顺手收集 text 事件（事件合同：用 event["type"] 收窄，和 agent 层内部同款写法）：

@router.post("/agent/stream")
async def agent_stream(payload: ChatCreate):
    # 1. body 阶段:与原来一致(建/查会话 → claim)
    async with AsyncSessionLocal() as db:
        if payload.conversation_id is None:
            conversation = await chats.create_conversation(db)
        else:
            conversation = await chats.get_conversation(db, payload.conversation_id)
            if conversation is None:
                raise HTTPException(status_code=404, detail="会话不存在")
    conversation_id = conversation.id
    await claim_conversation(conversation_id)

    async def event_generator():
        try:
            # 2. 装载短会话:存 user → 读全量 → 顺路读记忆
            async with AsyncSessionLocal() as db:
                conversation = await chats.get_conversation(db, conversation_id)
                if conversation is None:
                    raise HTTPException(status_code=404, detail="会话不存在")
                await chats.append_message(db, conversation, "user", payload.message)
                rows = await chats.get_conversation_messages(db, conversation)
                mem_rows = await memories.get_all_memories(db)

            history = trim_history([chats.message_to_dict(m) for m in rows])
            system_prompt = build_system_prompt([m.content for m in mem_rows])
            existing_texts = [m.content for m in mem_rows]
            llm_messages = build_llm_messages(history, system_prompt)
            new_stored: list[MessageDict] = []

            # 3. 流式 loop:透传事件,顺手把 text 收拢成全文(供提取用)
            reply_parts: list[str] = []
            async with _llm_semaphore:
                async for event in run_agent_stream(llm_messages, new_stored):
                    if event["type"] == "text":
                        reply_parts.append(event["text"])
                    yield f"data: {json.dumps(event, ensure_ascii=False)}\n\n"

            # 4. 记忆提取:流已收敛,秒级 await,零 DB 连接
            try:
                new_memory_texts = await extract_new_memories(
                    payload.message, "".join(reply_parts), existing_texts
                )
            except Exception:
                new_memory_texts = []

            # 5. 轨迹收敛后单事务写入(方案 B 不变) + 记忆写入
            async with AsyncSessionLocal() as db:
                conversation = await chats.get_conversation(db, conversation_id)
                if conversation is None:
                    raise HTTPException(status_code=404, detail="会话不存在")
                await chats.append_messages(db, conversation, new_stored)
                await memories.add_memories(db, new_memory_texts)
        finally:
            await release_conversation(conversation_id)

    return StreamingResponse(event_generator(), media_type="text/event-stream")
注意 SSE 的时序代价 提取插在「流收完」和「写轨迹」之间——用户此时已经看完了回复，但请求还没结束（前端 SSE 还挂着）。 多出的一次提取调用（约 1~2 秒）对用户体验几乎无感，因为正文早已吐完。 如果以后做「请求彻底结束」的收尾事件，记得提取在它之前。

05思考题（先自己想，再看详解）

Q1 · 为什么提取调用放在「收敛块之前」，而不是塞进收敛块里、或者挪到轨迹写完之后？ 详解：三个位置三种命运。块内：违反连接纪律——提取是秒级 await，session 会陪着 LLM 思考， 连接池被白占（并发 8 个请求 = 8 个连接陪跑）。轨迹写完之后：功能上可行，但提取失败就要靠 catch 兜住 才不影响 release；而且「先记后写轨迹」和「先写轨迹后记」相比，前者把 best-effort 的部分放在关键路径之外， 轨迹写入失败时（罕见）记忆也就不该写入——顺序本身就是语义。当前顺序：LLM 说话（零连接）→ 提取（零连接）→ 一次短连接收尾（轨迹+记忆），全程没有任何连接陪 LLM 思考。
Q2 · 如果把 system prompt 当成一条 role="system" 的消息存进 messages 表，会发生什么连锁反应？ 详解：① get_conversation_messages 返回它 → build_llm_messages 现在不认 system 角色，它被静默丢弃（改代码认它）→ ② 每次注入记忆都 append 一条新的 system → 同一会话第 10 轮时 装载出 10 条重复的旧 system → ③ trim_history 按条数裁剪，system 占坑挤掉真实对话 → ④ 最要命的是记忆更新后， 旧的 system 快照永远是错的。四环相扣，结论回到铁律：system 是每轮现拼的投影，不是历史。
Q3 · 「解析失败返回空」的降级策略，边界在哪？如果把这套静默降级用在 /agent 的轨迹写入上行不行？ 详解：不行，也不需要。降级策略的合法性取决于失败的代价结构：记忆漏一条，用户下次发现它忘了—— 可容忍；轨迹漏半截，下次装载直接 400，用户会话永久损坏——不可容忍，所以轨迹必须是强一致的单事务， 失败要暴露（让 500 发生、让 claim 释放后重试）。同一段代码风格，用在两个地方一个对一个错， 判断依据不是代码美学而是失败语义。这也是 error-as-data 不是银弹的原因：它是工具层的局部选择， 不是全局哲学。
Q4 · 算一笔账：记忆全量注入，每条平均 20 token。注入 50 条是多少？对照 /agent/stream 单轮的 token 预算，几条记忆开始「全量注入」变得不可接受？怎么办？ 详解：50 × 20 = 1000 token 的 system，加上工具简历（3 内置 + 2 记忆 + N 个 MCP）和历史， 单轮 prompt 轻松破几千 token——记忆还没开始干活就吃掉预算。更重要的是它线性增长且永不衰减。 出路就是问题三的另一条路：检索式注入——记忆入库时顺手 embed（L6 的合同原样复用）， 每轮用「当前用户消息」向量查 top-k 相关记忆再拼 system。记忆从「全量背诵」变「按需回忆」。 这一步不必现在做，但 memories 表设计时没锁死 content（没加唯一约束、没加 embedding 列）， 就是为了给这一步留门。
Q5 · /stream 要不要接入记忆？（动手题） 详解：注入侧应该接（它也是对话，没理由装失忆）；提取侧可以接（user 消息 + assistant 全文照喂）。 代码和 /agent 同构，两处改动。但建议先别动：C3 结业盘点时 /stream 的去留要拍板—— 如果砍掉，这活就白干了；如果留下，把它当成你自己不看答案的第一次独立接入。 判断练习：先读一遍 /stream 的现状代码，找出「装载点」和「收敛块」在哪，再决定加几行。
