专题插播 · T1 —— 进入 L8 之前的生态地图

Agent 生态三大件:SKILL / MCP / CLI

你每天都在用一个真实的 Agent——就是眼前这个 Claude Code。它会自己跑命令、会查资料、会连 MCP server、 会按 SKILL 手册办事。这一整套「外挂生态」的名词(SKILL、MCP、CLI、Hook、子 Agent、插件、CLAUDE.md) 最近一直在你眼前晃——还包括你写过的 CLAUDE.md 和配置过的权限规则(Rules)——但它们各自是什么、 边界在哪、什么时候用哪个,值得在进 L8 之前一次性钉死。 本课每个概念都锚定到你已经写过的代码(L4 工具注册表、L7 MCP)和你正在生效的配置 (CLAUDE.md、权限规则)以及路线图上将要写的课(L8 记忆、L9 上下文、L11 子 Agent) ——不是泛泛的名词科普,而是给你自己的项目画参照系。

01本课目标

  • 建立一张地图:CLI / MCP / SKILL 三条「给 agent 装能力」的路径,各自解决什么问题、边界在哪
  • 一句话认全周边概念:Hook / 子 Agent / 插件 / CLAUDE.md / Rules,并知道它们对应路线图上哪一课
  • 认识 Rules:约束的软硬光谱(CLAUDE.md 声明式条款 → 权限规则 → Hook)、层级叠加与写法实践

  • 动手:亲手写一个最小 SKILL(含脚本),在你的 Claude Code 里真实触发它
  • 每个概念对照你自己的项目:TOOLS_SCHEMA / TOOL_REGISTRY / McpClient 分别是生态里哪个角色的雏形

03CLI:agent 的手

CLI 为什么天然适配 agent

CLI(命令行程序)是四十年 Unix 哲学的产物,它有一套意外的、几乎是为 agent 量身定做的接口约定:

CLI 的老传统对 agent 意味着什么
stdin / stdout 是唯一接口模型天然读写文本——CLI 的输入输出就是模型的语言
exit code 表示成败(0 / 非 0)错误信号机器可读,agent 不用猜「刚才那步成功了吗」
可组合(管道、脚本)几个简单工具拼出复杂能力,不用每个都重新开发
无 UI、无状态、跑完即退agent 每次调用都是干净的一次性请求,不背会话包袱

所以在 Agent 时代,一个接口清晰的 CLI 本身就是一个现成的 agent 工具—— gh(GitHub 官方 CLI)、你机器上的 arkcli、Postman CLI 都是例子。 agent 拿着 Bash 这一个工具,理论上就能调用整个操作系统的所有 CLI。

Agent CLI:终端里的 agentic loop

反过来,把 agentic loop 本身做成一个 CLI,就是「Agent CLI」——Claude Code 就是这个词的标本: 你在终端里跟它对话,它在循环里读文件、跑命令、改代码。它有两种用法:

# 用法一:交互式(你现在正在用的)——人在回路里,每轮看结果
claude

# 用法二:headless 非交互——把 agent 当管道节点,给脚本/CI 用
claude -p "统计 app/ 下所有 py 文件的总行数" --output-format json

-p(print 模式)= 跑完自动退出、结果打到 stdout;--output-format json = 结构化输出(文本结果 + 用量统计等),方便上游程序解析。这一刻,agent 变成了一条可以被别的程序调用的命令—— CLI 既是 agent 的手,也可以是 agent 的壳。

Claude Agent SDK,一句话 把 Claude Code 的整套 harness(agentic loop、工具集、权限系统)以库的形式开放出来 (Python / TypeScript),让你不用从零裸写就能拥有同款 agent 运行时。 对你而言:你的 run_agent 是「库形式的 agent」(约两百行、完全透明), Claude Code 是「CLI 形式的 agent」(功能全、黑盒度更高)——同一种东西的两种封装,没有谁替代谁。

对照你的项目

你在 L4 给模型装的手是进程内函数(TOOL_REGISTRY 里的 Python 函数), CLI 是进程外程序(起个子进程跑完就退)。两者的模型侧接口完全一样——都是「工具简历 + 名字调用」, 差别只在执行器怎么落地。你的 scripts/l6_*.py 系列练习脚本, 就是「给 agent 用的 CLI 工具」的雏形:参数走命令行、结果走 stdout、出错返回非零。

04MCP:agent 的通用插座

先复习你写过的部分

MCP(Model Context Protocol)你在 L7 已经从字节层面裸写过了:JSON-RPC 2.0 做线格式, initialize → notifications/initialized → tools/list → tools/call 四步对话, stdio 做本地传输。所以本节不重复实现,只补生态视角——L7 课上没讲的那一半。

三种角色:host / client / server

角色是什么你项目里的对应物
Host用户面对的 agent 应用,管理多个 client你的 FastAPI 应用(整个 main.py + agent)
Clienthost 内部管理一条 server 连接的模块McpClient(一个实例管一个 server 子进程)
Server能力的提供方,暴露 tools / resources / promptsscripts/l7_mcp_server.py(你家知识库检索)

MCP 解决的是经典的 N×M 接法问题:M 个 agent 应用想接 N 种外部能力,两两各写一套对接 = N×M 份胶水代码。 有了标准协议,变成 N+M:server 作者只对 MCP 实现,host 作者也只对 MCP 实现,中间自由组合。 你 L7 的感受就是这个协议的价值——uvx mcp-server-time 一个第三方工具, 你的 client 没改一行协议代码就接上了。

三原语:你只用过 tools

MCP server 可以暴露三类原语(primitives),L7 你只实现了第一个:

原语语义类比
tools模型主动调用的函数(模型决定何时用)你的 TOOL_REGISTRY
resources应用主动拉取的数据(文件、记录,应用决定何时读)—(L7 没做)
promptsserver 预制的提示词模板(用户显式选用)—(L7 没做)

区分口诀:谁控制时机。模型控制 → tool;应用控制 → resource;用户控制 → prompt。 另外协议还定义了 client 侧能力(让 server 反过来请求 host 做事):sampling(server 借 host 的模型做推理)、 roots(server 感知 host 的文件系统范围)、elicitation(server 向用户要补充输入)——知道有这回事即可。

传输层演进:协议版本时间线

MCP 是一个活的协议,版本号就是日期。到本课写作时(2026-10),演进如下:

版本关键字
2024-11-05首版:stdio + HTTP+SSE 两种传输
2025-03-26Streamable HTTP 取代 HTTP+SSE:单端点、可断流重连
2025-06-18鉴权与安全细化——你 client.py 握手时报的就是这个版本号
2025-11-25上一代稳定版(2026-07-28 的变更基线)
2026-07-28(现行)迄今最大修订:无状态核心(去掉 Mcp-Session-Id、去掉 GET 流端点)、 多轮往返请求(MRTR)、扩展(Extensions)框架、Tasks、鉴权加固;官方 SDK 月下载近 5 亿次

怎么读这张表:stdio 至今是本地传输的主力,你的裸写知识完全不过时; 大修订集中在远程传输——方向是「让 MCP server 像普通 HTTP 服务一样无状态部署、水平扩容」。 你 L7 只做了 stdio,Streamable HTTP 在机动专题清单里,到时候 stdio 的 JSON-RPC 知识直接平移。

MCP 的代价:简历常驻(本课最重要的伏笔) MCP 工具的 schema 是启动时全量注入、每轮常驻上下文的(你的 get_all_tool_schemas() 就是这么聚合的)。装一两个 server 很爽; 装 20 个、每个 15 个工具,300 份简历每轮都发——token 先炸,模型选择精度也会被稀释。 这个问题怎么解?看下一节。
什么时候才值得写 MCP server 能力要被多个 host 复用(你家的检索想让 Claude Code、别的 agent 都能用)、 接的是外部系统(时间、天气、公司内部系统)、需要标准协议换取生态兼容——这些时候写 MCP。 如果只是自家 app 自家用的进程内函数,TOOL_REGISTRY 反而更简单: 别为了 MCP 而 MCP。你 L7 的 search_knowledge_base 包成 server,动机是「练习协议」, 真实项目里它就是个进程内工具。

05SKILL:agent 的操作手册

SKILL 是什么:一个目录

Agent Skills 是 Anthropic 于 2025 年提出的开放格式(仓库 anthropics/skills, 已被多家 agent 产品采纳)。一个 skill 就是一个文件夹,长得像你给新同事写的 onboarding 手册:

py-hand-check/                  ← skill 目录,名字即 skill 名
├── SKILL.md                    ← 必需:YAML frontmatter + Markdown 正文
├── scripts/                    ← 可选:可执行脚本(确定性步骤)
├── references/                 ← 可选:按需加载的详细文档
└── assets/                     ← 可选:输出时才用的模板/素材
# SKILL.md 的头部(frontmatter),name 和 description 是必需字段
---
name: py-hand-check
description: Python 代码自查清单。写完/改完 Python 代码后、被要求检查代码时使用。←...
---

# 下面是正文:给模型看的操作步骤(Markdown)

核心机制:渐进式披露(progressive disclosure)

这是 SKILL 与 MCP 工具的本质差异。skill 的内容分三级、按需加载:

级别内容何时进上下文体积
L1 元数据frontmatter 的 name + description会话启动,常驻 system prompt每个约几十 token
L2 正文SKILL.md 的 Markdown 正文模型判断「这个 skill 和当前任务相关」时几百到几千 token
L3 附属references/ 文档、scripts/ 脚本正文引用了才读/才执行不限

对比一下账就明白了:30 个 MCP 工具 = 30 份完整简历常驻;30 个 skill = 30 个一句话简介常驻, 正文只有被点名的那个才翻开。装一百个 skill 也不炸上下文——这就是 Anthropic 工程博客里 「为什么我们停止造专用 agent、改造 skill」的答案:能力可以无限堆,注意力成本恒定。

description 是路由键

模型凭什么决定「翻不翻开某个 skill」?只凭 L1 的那一句 description。 所以官方要求 description 必须同时说清「做什么」+「什么时候用」,写得含糊,自动触发就失灵 ——本课验证实验会亲手做这个对照。同理,skill 多了以后,description 之间会「抢路由」: 写得越像,模型越分不清该翻哪个。

脚本:确定性的事交给代码

skill 里的 scripts/ 是点睛之笔:模型不亲自逐步执行手册里机械的部分, 而是调脚本来跑,自己只负责判断和编排。比如「按规范校验一个 PDF」: 用哪个库、什么参数、怎么校验字段——这些确定性步骤写进 Python 脚本;「这份 PDF 的处理结果合不合理」 ——这个判断留给模型。口诀:模糊的事让模型判断,确定的事让代码执行。 你马上会在动手环节写一个这样的脚本。

解剖你机器上的真实标本

你的 ~/.claude/skills/ 下躺着 28 个真 skill,两个典型:

# 标本一:标准三段式(元数据 + 脚本 + 按需文档)
byted-web-search/
├── SKILL.md            ← frontmatter: name / version / author / description / metadata
├── scripts/web_search.py   ← 搜索就是跑这个脚本(Bash 调用)
└── references/         ← quick-start / setup-guide / troubleshooting 三份按需文档

# 标本二:description 写成「调度入口」
arkcli-doctor/
├── SKILL.md            ← description 里直接写了「什么情况走我 / 什么情况归别的 skill」
└── references/         ← 8 份细分文档:错误码、各 scope 的诊断手册……按需加载

注意两个细节:① byted-web-search 的正文里写着「脚本在鉴权失败时引导配置」—— 手册和脚本是一体的;② arkcli-doctor 的正文第一句是「MUST 先读 ../arkcli-shared/SKILL.md」——skill 之间可以互相引用, 形成「总纲 → 分册」的文档树,这正是 L3(附属文件按需加载)的实际用法。 另外目录里还有个 .arkcli-managed-skills.json:26 个 skill 名对着一串哈希—— 托管安装:skill 像软件包一样由工具统一分发、校验、升级。

SKILL vs MCP:一张对照表(本课灵魂)

SKILLMCP server

概念一句话本质进上下文吗你身边的活例子 / 路线图对应
Hook 在 loop 的固定事件(工具调用前/后、提交提示词时……)自动执行你预设的命令——确定性拦截点 不进。是代码级硬约束,不是给模型的提示 你今天亲眼见过:本课的课件就是在一个被 hook 管着的会话里写的——会话有 UserPromptSubmit hook(每轮注入路由规则)和 PreToolUse hook(拦下过一次格式错误的工具调用)。 prompt 是软约束,hook 是硬约束。→ L12 工具审批(human-in-the-loop)是它的应用
子 Agent 一个拥有独立上下文的 agent 实例,干完活只把结论带回主上下文 只有结论回主上下文 = 上下文隔离 主 agent 委托脏活(翻几十个文件),自己不被过程垃圾污染。 Claude Code 的子 agent 定义在 .claude/agents/*.md。 → 你将在 L11 spawn_subagent 裸写它
插件 把 skills + 命令 + 子 agent + hooks + MCP 配置打包分发的单元 安装时引入,机制同各部件 你机器上 26 个 arkcli-* skill 就是托管分发的活标本(.arkcli-managed-skills.json 记录哈希)
CLAUDE.md / AGENTS.md 声明式的项目指令与记忆,会话启动时常驻注入(全局 → 项目逐层叠加) 常驻(和 SKILL 正文相反!) 你这个项目就有两份在同时生效:用户全局 ~/.claude/CLAUDE.md + 项目 CLAUDE.md。它就是「人肉长期记忆」→ L8 要让你的 bot 自己拥有它;层级与写法见 07 节
权限模式 / 沙箱 工具执行的闸门:允许/询问/拒绝,settings.json 里配置 不进(闸门本身),但结果会进 你项目里的 .claude/settings.local.json 就在干这个;写法见 07 节
记忆口诀 CLI 给手,MCP 给插座,SKILL 给手册;Hook 给闸门,子 Agent 给分身,CLAUDE.md 给性格,Rules 给章程。 这些机制全部长在同一个 agentic loop 上——你 L5 写的那个循环,就是整个生态的共同底座。 Rules 的专门一节在下一节(07)。

07Rules:给 agent 定规矩

三大件之外还有一类东西你天天在受益:Rules——写成文件的约束条款。它不改模型、不写代码, 就是「把规矩写成仓库里的 Markdown / JSON,agent 每次干活时自动生效」。 你项目的 CLAUDE.md、.claude/settings.local.json,都是 Rules。

约束光谱:从软到硬

「给 agent 定规矩」不是一个开关,是一条光谱——按强制力排列:

强度机制本质失败模式
最软对话里随口叮嘱一次性 prompt,关会话即失效下个会话全忘
软Rules 文件(CLAUDE.md / AGENTS.md / .cursor/rules)常驻注入的声明式条款——模型读了靠自觉条款太多/冲突时会被模型忽略
硬权限规则(settings.json 的 allow / ask / deny)工具执行的闸门——代码强制,模型绕不过配错就误伤:太松失去保护,太紧寸步难行
最硬Hookloop 事件上的确定性拦截,可审计、可改写、可否决写错会卡死正常流程

经验法则:风格、流程用软约束;安全、危险操作用硬约束;能用硬就别用软。 例:本项目「绝不写/改/删源码」写在 CLAUDE.md 里——是软约束,靠模型自觉遵守 (配合「课件与 CLAUDE.md 例外」白名单把范围收窄);如果某天要保证而不是期望, 就得加权限 deny 或 Hook——这就是软约束的边界。

Rules 文件的层级(你机器上的三层实况)

企业策略(组织下发,最高优先级)
  └─ 用户全局  ~/.claude/CLAUDE.md      ← 227 字节:你的个人偏好(Postman CLI 位置等)
       └─ 项目     CLAUDE.md(进 git)   ← 13.7 KB:团队规范(架构/类型/课件规范)
            └─ 子目录  CLAUDE.md          ← 深层模块的局部规矩,进入该目录才加载
   外加:@import 把长文档拆出去(如 @doc/style.md);/memory 命令快速编辑;
        AGENTS.md(开放标准)同样被读取;另有 Claude Code 的自动记忆(auto memory)

规则:逐层叠加、就近优先——全局放个人偏好,项目放团队规范,都进同一条 prompt。 这套层级你已经在受益:模型此刻知道「全程中文」(全局层)也知道「参数必须标注」(项目层)。

行业对照:各家方言,同一个思想

趋同点一眼可见:仓库里的 Markdown 就是给 AI 的章程。你写项目 CLAUDE.md 练的不是某家工具的用法, 是整个行业的通用做法——以后换任何 agent 工具,这套习惯直接平移。

权限规则:硬约束的写法

权限写在 .claude/settings.json(团队,进 git)或 .claude/settings.local.json(个人,不进 git)。你项目里现在就有真实配置:

{
  "permissions": {
    "allow": [
      "Bash(arkcli auth *)",                                // arkcli 认证命令免确认
      "Bash(git log --oneline -8 ...)"                      // 看日志免确认
    ]
  }
}

// 规则语法 = 工具(限定模式):
{
  "permissions": {
    "allow": ["Bash(uv run ruff *)", "Read(doc/**)"],      // 放行:常用安全命令
    "ask":   ["Bash(git push *)"],                          // 每次人工确认
    "deny":  ["Read(.env)", "Read(**/secrets/**)"]         // 直接拒绝:秘密文件
  }
}

读法:allow 免问、ask 弹窗确认、deny 直接拒绝。 你平时看到的「允许运行这个命令吗」弹窗,就是这条配置面的运行时形态——同类命令弹烦了, 就把它写进 allow(本机的 arkcli 规则就是这么来的)。

写好 rules 的五条实践(本项目现身说法)

  1. 命令式、可判定:「参数必须标注,返回类型省略」是好条款——能逐条对照执行; 「注意代码质量」是废话——模型只能敷衍。
  2. 正面指令优先:说「要做什么」比「别做什么」管用;禁令难免时要具体 (「绝不写 app/scripts/配置」比「别乱动文件」强)。
  3. 放对层级:个人偏好进全局,团队规范进项目仓库——进 git 意味着可 review、可演进, 本项目 CLAUDE.md 的「类型规范」节就是团队规范长在仓库里的形状。
  4. 省着用:rules 常驻上下文,每条都是每轮的 token 成本。长文档用 @import 拆走, 「按需才用得上的方法」挪去 SKILL——常驻 vs 按需,又是那道 token 经济题。
  5. 软硬结合:条款写进 rules(模型知道),执行靠权限/Hook 兜底(系统保证)——两层都到位才闭环。
辨析:同一件事放对地方 章程常驻(Rules 文件)、方法按需(SKILL)、闸门硬来(权限规则)、拦截到点(Hook)。 例:「不许 push 到 main」——写 CLAUDE.md 是提醒,写 deny 是保证; 「删库前必须人工确认」——ask 规则挡一道 + Hook 审计一道,双保险。

08动手:写一个最小的 SKILL 并让它真实触发

现在轮到你了。目标:写一个叫 py-hand-check 的个人 skill—— 「Python 代码自查手册」,内容就按你自己的手滑史定制(拼写 contet/emial、类型标注、验证步骤)。 学完它就是你以后写代码的自动质检员。全程只动 ~/.claude/skills/,不碰项目源码。

认现场

先看看你机器上已经有什么:

ls ~/.claude/skills/
find ~/.claude/skills/byted-web-search -type f   # 看一个标准 skill 的结构

观察点:26 个 arkcli-* + byted 两个;byted-web-search 是标准三段式 (SKILL.md + scripts/ + references/)。这就是你接下来要模仿的形状。

建目录 + SKILL.md

mkdir -p ~/.claude/skills/py-hand-check/scripts

创建 ~/.claude/skills/py-hand-check/SKILL.md,全文如下(可直接抄,建议读一遍再抄——每行都有讲究):

---
name: py-hand-check
description: Python 代码自查清单。写完或改完任何 Python 代码后、或被要求检查/审查代码时使用。检查项:变量拼写手滑(如 contet/emial/DATATBASE_URL)、函数参数类型标注、泛型参数化(dict/list 不裸写)、改动后是否跑了 ruff 与 mypy 验证。
---

# py-hand-check:Python 代码自查清单

## 第一步:拼写扫描(确定性的事,交给脚本)

对目标文件运行扫描脚本:

    bash ~/.claude/skills/py-hand-check/scripts/check_typos.sh <文件...>

脚本只找已知手滑词。有输出 = 发现手滑,逐条改掉;输出「通过」则继续。

## 第二步:人工检查(需要判断的事,模型来)

按顺序核对:

1. **拼写与命名**:变量名是否手滑(重点:contet → content、emial → email、
   DATATBASE → DATABASE)。命名风格与所在文件既有风格一致。
2. **参数类型标注**:推不出类型的参数必须标;`dict` / `list` 裸写不行,要参数化
   (如 `dict[str, object]`);返回类型不写。
3. **Any 边界**:json.loads / 外部响应的 Any 结果必须就近收窄
   (isinstance + cast,或 pydantic 建形状),禁止链式裸取。

## 第三步:验证(不可跳过)

    ruff check <改过的文件>
    mypy <改过的文件>

两条都绿了才算完。跳过验证 = 本次检查不合格。

## 输出格式

按「✅/❌ 检查项 → 位置 → 建议」列表汇报,最后一行给结论。

讲解:① description 同时写了「做什么」(自查清单)和「什么时候用」 (写完/改完代码后、被要求检查时)——这是路由键,一字值千金; ② 正文第一步把机械活推给脚本、第二步才是模型的判断活——「确定交给代码,模糊交给模型」; ③ 检查项直接取自你项目的真实规范——skill 就是这么沉淀个人/团队规范的。

写脚本

创建 ~/.claude/skills/py-hand-check/scripts/check_typos.sh:

#!/usr/bin/env bash
# 已知手滑词扫描:命中则打印行号并退出 1,通过则退出 0
TYPOS="contet|emial|DATATBASE|retrun|lenght|publich"

if [ $# -eq 0 ]; then
    echo "用法: check_typos.sh <文件...>"
    exit 2
fi

matches=$(grep -nE "$TYPOS" "$@")
if [ -n "$matches" ]; then
    echo "$matches"
    echo "发现手滑词 ↑"
    exit 1
else
    echo "拼写扫描通过"
fi

加执行权限并自测:

chmod +x ~/.claude/skills/py-hand-check/scripts/check_typos.sh
echo "contet = 1" > /tmp/typo_demo.py
bash ~/.claude/skills/py-hand-check/scripts/check_typos.sh /tmp/typo_demo.py   # 期望:命中并 exit 1

讲解:注意 exit code 的语义设计——0 通过、1 发现问题、2 用法错误。 agent 看 exit code 就知道走哪条分支,这就是 03 节说的「CLI 是 agent 友好接口」的全部含义。

触发方式 A:显式调用

开一个全新的 Claude Code 会话(skill 清单在会话启动时注入),输入:

/py-hand-check

它会把 skill 正文当成指令载入。给它一个靶子:

/py-hand-check 检查 /tmp/typo_demo.py

观察点:它应该先跑 check_typos.sh,然后按清单逐项汇报。 如果它问「允许运行 bash 命令吗」——这就是权限闸门(06 节表格里的最后一行)在工作。

触发方式 B:自动路由

再开一个新会话,这次不点名 skill:

帮我自查一下 /tmp/typo_demo.py,看看有没有问题

观察点:它应该自己决定翻开 py-hand-check(因为你的请求和 description 匹配)。 它会告诉你它用了什么 skill;若没有,说明 description 的「何时用」写得不够命中——下一节实验会系统验证这件事。

清理与坑 全部练完想删除:rm -rf ~/.claude/skills/py-hand-check 即可,无副作用。 常见坑:① 忘了开新会话——旧会话的 skill 清单是启动时注入的,新建的 skill 在旧会话里不存在; ② frontmatter 的 --- 必须顶格、必须成对;③ description 别写成一句空话, 「做什么 + 何时用」缺一不可。

09思考题(含详解)

Q1 · SKILL 的 description 和 MCP 工具的 description,都在帮模型做选择,本质区别是什么?

详解:两者都是「给模型的信号」,但经济模型完全不同。

MCP 工具的 description 挂在 schema 上,每轮都参与工具选择——模型每一步都要在全部工具简历里挑一个, 所以简历必须常驻、必须写好,数量一多就稀释注意力(SKILL 一节开头说的代价)。

SKILL 的 description 是一次性的路由决策:只在「要不要翻开这本手册」时被比对, 翻开之后正文接管,没翻开就只花那几十个 token 的元数据成本。

一句话:工具 description 是常驻的选票,skill description 是按需的目录页。 这就是「渐进式披露」在 token 经济上的意义——L9 上下文工程的所有技巧,都是在做同一道题。

Q2 · 三个需求,各选什么载体?① 给 agent 接入公司 Jira;② 沉淀团队的 Python 代码规范;③ 让 agent 能查快递——快递公司已有成熟 CLI。

详解:

① MCP server。外部系统、多 host 复用、需要标准化的连接与鉴权——教科书场景。 (顺带:Jira 官方就有 MCP server,先找现成的,再考虑自己包。)

② SKILL。这是纯粹的程序性知识——没有「连接」任何外部系统,只是「怎么写代码」的方法论。 放 .claude/skills/(项目级)让团队共享,或插件分发。

③ 直接 Bash 跑 CLI,三个都不用做。机器接口已经完备(stdin/exit code), 包一层 MCP 或 skill 都是多余——MCP 的价值在标准化复用,CLI 已经是事实标准了。 值得做的只是:在 CLAUDE.md 或 skill 里写一句「查快递用 xxx CLI,参数这样传」, 把用法知识补上,而能力本身不包装。

判别标准汇总:要连接外部系统且多方复用 → MCP;要沉淀方法与规范 → SKILL;机器接口已完备 → 裸 CLI。

Q3 · CLAUDE.md 和 SKILL.md 都是 Markdown、都会进上下文,区别在哪?

详解:三个维度。

装载时机:CLAUDE.md 常驻(每次会话启动必注入);SKILL 正文按需(和任务相关才翻开)。 所以 CLAUDE.md 要短、要金贵——它是你最贵的 token 地产;SKILL 可以长——反正不常用不付费。

内容性质:CLAUDE.md 回答「我是谁、这里的规矩是什么」(人格、约定、边界); SKILL 回答「做某件事的流程是什么」(程序性知识)。

与 L8 的关系(重点):CLAUDE.md 本质上是人类手写的、静态的长期记忆—— 你把「用户手滑模式」写进 CLAUDE.md,就是手动完成了一次「提取 → 存储 → 注入」。 L8 要做的事,是把这三个环节自动化:让 bot 自己从对话里提取记忆、存进 memories 表、 每轮自动注入 system。CLAUDE.md 之于 Claude Code,就是你 L8 的 memories 表之于你的 bot。

Q4 · 设计题:把你的 TOOLS_SCHEMA 改成「skill 式」两级加载,数据结构和流程怎么改?有什么坑?

详解:方向性方案(不是让你现在改代码,进 L9 时会回来用):

# 现在:全量常驻
TOOLS_SCHEMA: list[ToolParam]            # 每轮整张简历表都发

# skill 式:两级
TOOLS_INDEX: list[ToolCard]              # 常驻层:仅 name + 一句话简介
_TOOL_DETAIL: dict[str, ToolParam]       # 仓库层:完整 JSON Schema

# 再注册一个元工具,让模型按需取详情:
#   get_tool_detail(name) -> str   (从 _TOOL_DETAIL 里查,返回 schema JSON)

流程:每轮只发 TOOLS_INDEX → 模型想用某工具时先调 get_tool_detail 拿参数定义 → 再正式调用。

坑(想清楚这三条才算想清楚):① 多了一次往返,延迟和轮次成本上升——工具少时是纯亏, 所以这是「工具多到一定规模才启用」的策略;② 模型可能不查详情就瞎猜参数—— 必须在 ToolCard 的一句话简介里写死「调用前必须先 get_tool_detail」,用提示词约束; ③ execute_tool 的必填校验(_validate_required) 目前依赖 TOOLS_SCHEMA 全量在场,拆表后它得改查 _TOOL_DETAIL—— 改合同要同步改所有使用侧,你在 L5 就吃过 MessageDict 漏改的亏,这里同理。

10验证实验

实验一:description 对照实验(证明「路由键」)

① 新会话,问「帮我检查 /tmp/typo_demo.py 这段 Python 代码」→ 观察 py-hand-check 被自动触发。

② 把 SKILL.md 的 description 改成一句含糊的话:

description: 一个工具。

③ 新开会话,问一模一样的问题 → 观察自动触发失灵(它不知道「检查代码」该翻这本手册)。

④ 改回原文,再验证恢复。

结论:自动触发完全依赖 description——元数据就是路由表,正文写得再好,路由失败就没人翻。

实验二:headless 用法 + 结构化输出

claude -p "列出你当前能看到的 skill 名字,一行一个" --output-format json | head -30

观察点:① 输出是 JSON(结果文本 + 耗时/用量字段)——这就是 agent 被当「管道节点」用的样子; ② 结果里应该能找到 py-hand-check 和那些 arkcli-*——L1 元数据确实常驻在 system prompt 里。 对比:跑一次 claude -p "1+1=?",看用量字段, 感受一下「常驻元数据」本身也是每轮的固定成本。

实验三:MCP 现状盘点

claude mcp list        # 项目根目录下跑

以及在交互会话里输入 /mcp。

观察点:列出你已配置的 MCP server(本机目前挂着搜索、数据检索、VS Code 等几个), 每个下面是它的工具清单。对照 04 节:这就是「host 已经替你当好了」—— 你在 L7 手写的 McpClient 三连,每天都被 Claude Code 在后台跑无数遍。

实验四(选做):脚本化的确定性

往 /tmp/typo_demo.py 里再加一个手滑词(比如 retrun), 再走一遍自动触发。观察它先跑脚本拿到精确行号、再做人judgment—— 两层分工和 05 节讲的完全一致。把 SKILL.md 第一步删掉再试,对比它是否开始「肉眼找 bug」—— 没了脚本,确定性的活也落回模型头上,又慢又不可靠。
