Redis 分布式互斥

B2 的会话互斥（claim/release）靠一个进程内的 set——--workers 4 一开它就失效。 本课把在途表搬进 Redis：SET NX EX 一条命令拿下「检查 + 占位」的原子性。 这也是下一课 Docker 部署的地基：容器内多 worker 的正确性靠它。

01本课目标

  • 理解进程内互斥在多 worker 下为什么必然失效（不是写法问题，是状态位置问题）
  • 掌握 Redis 分布式锁三件套：NX（互斥）+ EX（崩溃自愈）+ 配对 DEL（释放）
  • 动手：claim/release 换 Redis 实现，六个调用点补 await，lifespan 收尾连接池
  • 验证：多 worker 下同会话并发 409 从「看运气」变「稳定复现」
前置条件 compose 里已有 redis 服务。确认它在跑：docker ps | grep redis。 没起的话：docker compose up -d redis。

02背景回顾：进程内方案是怎么失效的

B2 的互斥依赖一个模块级变量：

# 进程内在途会话表:同会话同时只允许一个请求在跑
_busy_conversations: set[int] = set()

单 worker 下它是正确的：asyncio 协作式调度里，「检查 + add」之间没有 await，事件循环不会切走，天然原子。

但 --workers 4 会把整个应用复制成 4 个独立进程——每个进程 import 一遍模块，就有 4 张互不相识的表：

请求A(会话20) ──┐
                ├──> worker-1: _busy_conversations = {20}   ← 登记在自己的表里
                │
请求B(会话20) ──┐
                ├──> worker-2: _busy_conversations = {}    ← 看不见 worker-1 的 20!
                │             检查 20 不在 → 放行 → 两个 agent 交错写轨迹 → 乱序

两个请求落在同一个 worker 就会 409，落在不同 worker 就都放行——互斥变成了掷骰子。 掷骰子式的正确性比确定性 bug 更危险：测试时可能恰好都命中同一 worker 显得「还能用」，上线后轨迹乱序、半截轨迹 400 会不定时回来。

结论 互斥状态必须存在所有进程都能看到的地方。compose 里躺着的 redis 正是干这个的—— 同一个会话项目的 DB、缓存、互斥表，都应该是「进程之外」的基础设施。

03原理：SET NX EX，一条命令的原子性

Redis 的 SET 命令带两个修饰参数，一条命令同时表达三件事：

SET chat:busy:20 "1" NX EX 600
│        │        │   │   └─ 过期时间 600 秒(key 到点自动消失)
│        │        │   └─ NX = 不存在才设置(key 已存在则失败,返回 nil)
│        │        └─ value(我们不需要值本身,只是占位)
│        └─ key = 业务前缀 + 会话 id
└─ 返回 OK = 拿到锁;返回 nil = 已有人在途 → 409

为什么一条命令就够，而进程内版要「检查 + add」两步？

原子性的归属变了。进程内两步不出本进程内存，安全靠「之间没有 await」； 跨进程后，判断和写入要经过网络到 Redis——如果先 GET 再 SET， 两个 worker 可能在同一瞬间都 GET 到「不存在」，然后都 SET 成功，互斥击穿。

SET NX 把「存在性判断 + 写入」压缩成 Redis 服务端的单条命令。 Redis 命令处理是单线程串行的，天然原子——竞态被整体外包给了 Redis。

TTL 是崩溃兜底，不是精确的锁计时器

如果持有锁的进程崩了（kill -9、断电、OOM），finally 里的 release 永远不会执行， key 会永远留在 Redis 里——那个会话被永久锁死。EX 就是兜底：600 秒后 key 自动消失，服务自愈。

取值依据：远大于 agent 最坏执行时长（MAX_ROUNDS=8 轮 LLM + 工具，分钟级封顶），600 秒留足余量。 太短（比如 60 秒）会在 agent 还在跑时提前放锁，互斥失效；太长则真崩溃后该会话恢复得慢。

目标时序

worker-1 的请求A 和 worker-2 的请求B,竞争会话 20:

A: SET chat:busy:20 "1" NX EX 600  →  OK      拿到,开始跑 agent
B: SET chat:busy:20 "1" NX EX 600  →  nil     已存在 → 409「该会话正在处理中」
...A 跑完 agent,写轨迹...
A: DEL chat:busy:20                →  OK      release
B': SET chat:busy:20 "1" NX EX 600 →  OK      下一轮请求正常进来

04动手实现（6 步）

安装依赖

uv add redis

redis-py 从 4.2 起内置 asyncio 支持（redis.asyncio），不需要额外的异步包。

配置：Settings + .env

app/config/config.py 的 Settings 加字段：

# Settings 类里
redis_url: str = ""

.env 配真实地址（带密码，密码来自 compose 的 redis 服务）：

REDIS_URL=redis://:redis123@localhost:6379/0
点评：「空默认 + .env 必配」是合理选择 默认值给空串而不是 redis://localhost:6379/0，和项目里 DATABASE_URL 同一个哲学： 必填项不提供能跑通的假默认——from_url("") 会直接抛错，.env 漏配在启动第一秒就暴露，而不是运行到互斥时才奇怪。 真实 URL 语法复习：redis://:密码@主机:端口/库号，冒号前留空 = 无用户名只有密码。
别忘了模板 .env.example 是仓库里的配置模板，要同步加 REDIS_URL=（值写占位即可），别人 clone 下来才知道需要配什么。

基础设施层：app/database/redis_client.py

落地文件全文（与仓库一致）：

import redis.asyncio as Redis

from app.config.config import settings

redis_client = Redis.from_url(
    settings.redis_url,
    decode_responses=True,
)


async def get_redis():
    return redis_client

结构完全正确：模块级单例 + from_url 惰性连接（import 时不握手，第一条命令才连，无需 lifespan 启动项）+ decode_responses=True（返回 str 而不是 bytes，我们存取的都是简单字符串）。位置也对：database/ 归管所有外部连接。两个风格点评：

  • 别名 as Redis 大写：PEP8 里大写驼峰留给类，模块别名惯例小写。容易混淆的点：redis.asyncio 包里恰好有个 Redis 类——from redis.asyncio import Redis 然后 Redis.from_url(...) 是官方常见写法（此时 Redis 就是类）。你现在是「模块别名成了大写」，能用，但建议改成 from redis.asyncio import Redis 的类导入，或别名小写，二选一。
  • get_redis() 目前无人调用：路由是直接 from app.database.redis_client import redis_client 拿单例的。它要么删掉（不留死代码），要么明确它作为 FastAPI Depends 注入入口的定位——单文件单例场景直接 import 更直白，教学版建议删。

claim / release 换 Redis 实现

chats.py 顶部的 import 与常量见前两步，本步把两个函数换成 Redis 实现，并删除整个 _busy_conversations：

from app.database.redis_client import redis_client

# 锁 key 模板:业务前缀 chat: + 语义 busy: + 会话 id。
# 前缀分级是为了 keys/排查时一眼看出归属;TTL 是崩溃兜底,取远大于 agent 最坏执行时长
_BUSY_KEY = "chat:busy:{conversation_id}"
_BUSY_TTL_SECONDS = 600


async def claim_conversation(conversation_id: int):
    """登记在途,重复则 409。SET NX EX 单命令原子,跨 worker 共享。

    原「检查+add 无 await 无需锁」的论证随实现一起作废——现在有 await 了,
    但原子性整体外包给 Redis 的单命令,比进程内方案更强而不是更弱。
    TTL 是崩溃兜底:进程挂了没人 DEL,600 秒后 key 自动消失,服务自愈。
    """
    ok = await redis_client.set(
        _BUSY_KEY.format(conversation_id=conversation_id),
        "1",
        nx=True,
        ex=_BUSY_TTL_SECONDS,
    )
    if not ok:
        raise HTTPException(status_code=409, detail="该会话正在处理中,请等上一轮完成")


async def release_conversation(conversation_id: int):
    """解除在途登记,与 claim 配对使用。"""
    await redis_client.delete(_BUSY_KEY.format(conversation_id=conversation_id))
删干净 _busy_conversations: set[int] = set() 和它的注释一起删——留着会让人误以为进程内表还在参与工作。 旧版「检查 + add + discard」的全部逻辑都被上面两个函数取代。
两个函数都变成了 async 所有调用点必须加 await（下一步）。漏加的话 Python 只会拿到一个 coroutine 对象、什么都不执行，互斥静默失效—— 和 B2 时 try/finally 包错对象是同一种危险：不报错，但逻辑没跑。

调用点加 await（三处 claim + 三处 release）

三个接口的接入位置不变（claim 在响应头发出前，release 在 finally 里——B2 验收过的结构原样保留），只是都变成 await：

# 三个接口的 handler 里(body 阶段拿到 conversation_id 之后):
await claim_conversation(conversation_id)

# /agent 的 try/finally 与两个流式接口 generator 的 finally:
finally:
    await release_conversation(conversation_id)

generator 的 finally 里 await 没问题：aclose 触发 GeneratorExit 时，finally 依然是异步上下文，Redis 调用照常执行。

lifespan 收尾：关掉 Redis 连接池

# app/main.py — lifespan 的关闭段(yield 之后),mcp_client.stop() 旁边:
await mcp_client.stop()
await redis_client.aclose()   # 归还并关闭连接池,干净退出
# main.py 顶部 import 区
from app.database.redis_client import redis_client

05思考题（做完自问，想通才算懂）

Q1 · 为什么 SET NX EX 一条命令就行，进程内版却要「检查 + add」两步？ 原子性的归属不同。进程内两步都在本进程内存里，安全靠「之间没有 await，协作式调度不切走」。 跨进程后判断和写入要过网络，两步之间任何进程都可能插入，竞态重新出现。 SET NX 把「存在性判断 + 写入」压进 Redis 服务端单命令，原子性由 Redis 单线程串行模型保证。
Q2 · TTL 为什么 600 秒而不是 60 秒？ TTL 是崩溃兜底，不是精确的锁计时器。TTL < 正常执行时长时，agent 还在跑锁就过期了， 第二个请求进来，互斥失效。取值 = 远大于 MAX_ROUNDS 最坏执行时长。 权衡的另一头：TTL 越长，真崩溃后该会话恢复越慢（要等 key 过期）。 600 秒表达的是「误释放的风险 ≪ 恢复延迟」这个取舍。
Q3 · release 直接 DEL 有什么理论缺陷？ 可能误删别人的锁。时序：A 持锁 → A 卡顿超过 TTL → 锁自动过期 → B 拿到新锁 → A 恢复过来执行 DEL → 把 B 的锁删了 → C 也能进来，三方互斥崩塌。 严格解法：SET 时 value 存自己的随机 UUID，DEL 前用 Lua 脚本原子比对「是自己的才删」。 本项目 release 与 claim 严格配对、执行时长 ≪ TTL，风险可忽略——教学版从简，知道缺陷在哪即可。

观察点 1 · 启动日志

[mcp:kb] 握手完成 出现 4 次——lifespan 每个 worker 各跑一遍， 4 个进程各自 spawn 一个 MCP 子进程。这是 stdio 拓扑在多进程下的固有代价，看一眼有个概念即可。

观察点 2 · 并发 409 稳定复现

用同一个 conversation_id 并发打两个请求，反复跑 5 遍，记下每遍的结果：

curl -X POST http://127.0.0.1:8000/chat/agent -H "Content-Type: application/json" \
  -d '{"message": "详细讲讲向量检索的原理", "conversation_id": 20}' &
curl -X POST http://127.0.0.1:8000/chat/agent -H "Content-Type: application/json" \
  -d '{"message": "换个话题", "conversation_id": 20}'
wait

期望：5 遍全部稳定地一 200 一 409——「看运气」消失了，这就是 Redis 在起作用的直接证据。

观察点 3 · 亲眼看 key（可选）

请求进行中另开终端，观察 Redis 里的在途键（redis 设了密码，-a 传入）：

docker exec -it study-redis redis-cli -a redis123 keys 'chat:busy:*'

07对比小结

维度进程内 set（B2）Redis SET NX（本课）
状态可见范围单进程所有 worker / 所有容器
原子性来源协作式调度（检查+add 之间无 await）Redis 服务端单命令
进程崩溃后状态随进程消失（单进程下等于自愈）TTL 兜底自动过期
多 worker / 多实例 / 容器编排失效（本课动机）依然正确
新增风险无引入 Redis 可用性依赖：Redis 挂 → 互斥失效，需评估降级策略（进阶话题，暂不做）
本课灵魂知识点 ① 互斥状态要活在「进程之外」——凡是多 worker/多实例都要一致的东西，不能放进程内存。
② 「判断 + 写入」跨进程时必须压缩成服务端单命令（SET NX），否则竞态重现；分布式锁三件套 = NX（互斥）+ EX（崩溃自愈）+ release 配对。
③ async 化的函数，所有调用点必须跟上 await——漏了不报错，只是静默不执行。
