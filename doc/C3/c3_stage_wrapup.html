#实验期望观察

2Postman 打 /chat/agent：「北京现在几点」（触发 get_city_time 工具轮）200 + reply 里有时间；DB 里该会话出现 user / assistant(tool_calls) / tool / assistant 四条消息——方案 B 全量轨迹在容器里依然成立

4同 conversation_id 并发两个请求（C1 的 curl & 实验）跨容器依然稳定一 200 一 409——Redis 互斥在容器网络里一锤定音；反复 5 遍无例外
5docker compose restart app 后，拿第 2 步的 conversation_id 再发一条「我们刚才聊了什么」模型能复述之前内容——数据库是对话唯一真相源，app 容器无状态、重启不丢数据
6docker exec -it study-redis redis-cli -a redis123 keys 'chat:busy:*'为空——所有请求正常结束后锁无泄漏（TTL 兜底之外的正常路径）
7uv run ruff check app && uv run mypy app全绿——阶段 3 的每一步都没欠静态检查的债
第 5 项为什么值得单列？ 它验证的是「容器无状态 + 状态外置」这条生产部署的核心原则：app 容器可以随意销毁重建， 因为对话状态在 Postgres（消息）、在 Redis（互斥，且是短命 key）。反例是状态放进程内存—— C1 之前的 _busy_conversations 和 B2 之前的无持久化，重启即丢。终验不是走过场，是在验证架构决策。

06阶段 3 灵魂知识点汇总

带走这九条 ① 连接纪律：run_agent/stream_chat 等秒级 await 外不得有任何 AsyncSessionLocal 块——连接不陪 LLM 思考。
② 409 必须在响应头发出前抛；流开始后错误只能走流内事件，校验必须在 body 阶段。
③ async def 只是定义不执行——try/finally 必须包住 generator 的执行（放体内）而非定义。
④ 事务边界 = 语义单元：整条 agent 轨迹一个事务（append_messages），单条消息一个事务（append_message）。
⑤ 工具轮判定靠「攒没攒到申请单」，不靠 finish_reason；tool_calls 碎片按 index 拼接。
⑥ trim 切点后移到第一个 user——存储合同（轨迹完整性）约束 UI 层的截断策略。
⑦ 互斥状态活在进程之外；「判断 + 写入」跨进程必须压缩成服务端单命令（SET NX）；NX 互斥 + EX 崩溃自愈 + 配对 DEL。
⑧ 容器化配置分层：env_file 共性 + environment 拓扑差异；服务名即主机名；service_healthy 是就绪顺序声明。
⑨ 容器无状态 + 状态外置（Postgres 持久状态 / Redis 短命状态），app 可随意销毁重建。
