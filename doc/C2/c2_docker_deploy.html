阶段 3 生产化 · C2

Docker 部署收尾：app 进容器，compose 一键全栈

现状是「半编排」：db 和 redis 在 compose 里，app 本地 uv run 直跑。 本课解开 compose 里注释的 app 服务——配置注入（env_file + environment 覆盖）、容器网络主机名、 Dockerfile 微调，最后一套 docker compose up 起全栈。

01本课目标

  • 掌握容器化配置注入的分层：env_file 提供共性，environment 覆盖拓扑差异
  • 理解容器网络：服务名即主机名，localhost 在容器里指容器自己
  • 理解 depends_on + condition: service_healthy：把「启动顺序」升级为「就绪顺序」
  • 动手：compose 解开 app 服务 + Dockerfile 微调，三容器全栈跑通
前置条件 C1 的 Redis 互斥已落地（本课 app 容器会以 --workers 4 跑， 多 worker 正确性靠 Redis SET NX EX——若还停在进程内 set，容器里互斥等于掷骰子）。

02背景回顾：现状与资产盘点

前课地基（一句话）

C1 已把会话互斥从进程内 set 换成 Redis SET NX EX （key = chat:busy:{conversation_id}，TTL 600 秒，release 配对 DEL）—— 互斥状态活在「进程之外」，所有 worker / 所有容器共享同一份。

现有资产盘点（与仓库一致）

Dockerfile 已有（Docker 线产物），结构是标准的两段式：

FROM python:3.13-slim            # 精简版 Debian 基座
WORKDIR /app
COPY pyproject.toml uv.lock ./   # 先只拷依赖声明 —— 利用层缓存:代码改动不重装依赖
RUN pip install uv && uv sync --frozen --no-dev --no-install-project
COPY app ./app                   # 这时候才拷代码
COPY README.md ./
RUN uv sync --frozen --no-dev
EXPOSE 8000
CMD ["uv", "run", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

compose 现状：db（pgvector，healthcheck 齐全）+ redis（带 --requirepass，healthcheck 齐全）， app 服务整段被注释。解开它有四个问题要解决：

#问题解法
1.env 不进镜像也不进仓库，容器里读不到 ARK key 等配置env_file 挂 .env + environment 覆盖差异项（compose 规则：environment 优先级 > env_file）
2容器网络里 localhost 指容器自己，连不到 db/redis主机名改用服务名 db / redis（compose 内置 DNS）
3MCP 子进程（lifespan spawn 的 stdio server）在容器拓扑怎么办MCP_KB_SERVER_CMD 置空 → lifespan 的 if 自动跳过（这正是当初写这个判断的远见）；进阶方案见步骤 3
4注释版 app 服务自己的坑：DATABASE_URL 用户名写的是 study，但 db 服务定义的是 POSTGRES_USER: postgres——照抄必 500解开时修正为 postgres:study123@db:5432

03关键机制：配置怎么进容器、容器之间怎么找到彼此

配置注入的三层

层内容特点
镜像内代码 + 依赖（uv sync 装好的 .venv）没有 .env——它被 .gitignore 和 .dockerignore 挡在外面，这是对的
env_file宿主机的 .env 整体注入（ARK key 等共性配置）文件在宿主机上，不进镜像层、不进 git；compose 读它，不是 Docker build 读它
environment容器拓扑下的差异项（主机名、MCP 开关）写在 compose 文件里，优先级高于 env_file——同名的环境变量以它为准

这样分层的收益：本地直跑和容器跑用同一份 .env（localhost 版地址）， 容器只覆盖「拓扑不同」的三项——配置的共性留在文件，差异留在编排层。

容器网络：服务名即主机名

compose 会为项目建一个独立 bridge 网络，每个服务名注册成 DNS 名。 app 容器里 db 解析到 db 容器 IP、redis 解析到 redis 容器 IP。 而 localhost 永远指容器自身的回环——这是容器网络最常见的新手坑。

启动顺序 vs 就绪顺序

不带 condition 的 depends_on 只保证「容器被创建」的顺序——容器启动了不等于服务能用了 （Postgres 启动到能接受连接要几秒）。db/redis 的 healthcheck 探活命令已经写好在 compose 里， app 侧用 condition: service_healthy 引用，compose 会等到健康检查通过才启动 app—— 这不是装饰，是启动顺序的正确性声明。

04动手实现（3 步）

compose 解开 app 服务

把注释的 app: 段替换成（docker-compose.yml）：

  app:
    build: .                      # 用根目录 Dockerfile 构建
    container_name: study-app
    ports:
      - "8000:8000"
    env_file:
      - .env                      # ① 整体注入本地 .env(ARK key 等共性配置)
    environment:                  # ② 覆盖容器拓扑下的差异项(优先级高于 env_file)
      DATABASE_URL: postgresql+psycopg://postgres:study123@db:5432/study_fastapi
      REDIS_URL: redis://:redis123@redis:6379/0
      MCP_KB_SERVER_CMD: ""
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
要点 ① env_file 提供共性、environment 覆盖差异——这是 compose 的标准分层，ARK key 这类与拓扑无关的配置留在 .env，与拓扑相关的（主机名）在 environment 里改写。
② @db:5432 / @redis:6379 —— 服务名即主机名；用户名用 postgres（修正盘点表第 4 项的坑）。
③ depends_on 两个 healthy：redis 的 healthcheck 在 compose 里已就位，直接引用。

Dockerfile 微调

两处改动：

# ① 代码拷贝区补上 alembic(迁移要在容器里跑,见步骤 3;不跑迁移可不加)
COPY app ./app
COPY alembic ./alembic
COPY alembic.ini ./
COPY README.md ./

# ② CMD 加 --workers 4(与 C1 配合:Redis 互斥已跨进程安全,容器内多 worker 有靠山)
CMD ["uv", "run", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "4"]
讨论：容器内多 worker vs 容器单进程 生产上更主流的是容器内单进程，横向扩容交给编排层（compose scale / K8s replicas）——一个容器一个进程，崩溃边界清晰。 教学版选容器内 --workers 4：与 C1 的验证实验连续（日志、互斥行为完全一致），且 Redis 互斥保证多 worker 正确性。 知道两种形态的取舍即可。

可选进阶：容器启动自动迁移 + MCP 进容器

自动迁移：alembic/env.py 通过 settings.database_url 拿连接串——pydantic-settings 的优先级是环境变量 > .env 文件， 所以容器里 environment 注入的 DATABASE_URL 自动生效，容器内 alembic upgrade head 直接可跑。把 CMD 改成先迁移后起服务：

CMD ["sh", "-c", "uv run alembic upgrade head && uv run uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4"]

迁移在 CMD 层跑一次、先于 worker 启动——天然避开「4 个 worker 同时迁移」的竞态。

MCP 进容器（想让容器版也带知识库工具时）：scripts/ 拷进镜像，cmd 指向自家 server：

COPY scripts ./scripts
# compose 的 environment 里:
MCP_KB_SERVER_CMD: "uv run python scripts/l7_mcp_server.py"

注意 uvx 拉外部包（如 mcp-server-time）需要网络且缓存不持久，容器化优先用自家 stdio server。教学版保持置空也完全成立——内置工具照跑，只是少了 MCP 外接工具。

05思考题

Q1 · 为什么用 env_file + environment 覆盖，而不是把所有配置都写进 environment，或都打进镜像？ 全写 environment：ARK key 明文进 compose 文件，而 compose 文件通常进 git——密钥泄漏。 全打进镜像：密钥进了镜像层，任何拿到镜像的人 docker history / 导出就能翻出来，且改一个配置要重新构建。 env_file 方案里 .env 只存在于宿主机，不进 git 也不进镜像；environment 只放「不算秘密的拓扑差异」。
Q2 · 容器里 DATABASE_URL 的主机名为什么不能写 localhost 或 127.0.0.1？ 每个容器的网络栈是隔离的（network namespace），容器里的 localhost 指容器自身的回环——db 根本不在「本机」上。 它们靠 compose 的 bridge 网络互联，服务名注册为 DNS 名，所以写 db / redis。 本地直跑时 localhost 能通，是因为 db 端口映射到了宿主机——「能通」的原因完全不同。
Q3 · depends_on 不加 condition 和加 service_healthy 有什么区别？为什么 app 必须要后者？ 不加 condition 只保证创建顺序（容器启动 ≠ 服务可用）；Postgres 从启动到能接受连接有几秒窗口， app 启动即连 db/redis，撞上窗口就直接连接失败。 service_healthy 复用 healthcheck 的探活结果，把「启动顺序」升级为「就绪顺序」——app 启动时依赖必然已可用。

06验证

# 先停掉本地直跑的 uvicorn(8000 端口不能被占),然后构建并起全栈(首次构建要几分钟)
docker compose up -d --build

# 看三容器都 healthy、app 启动日志
docker compose ps
docker compose logs -f app

观察点

  1. 三容器全部 healthy：study-pgsql / study-redis / study-app
  2. app 日志：uvicorn 起 4 个 worker；[mcp:kb] 握手日志不出现（MCP 置空跳过的直接证据）；没有 REDIS_URL 相关报错
  3. curl http://127.0.0.1:8000/health → {"status":"ok"}
  4. 并发 409 复测：用 C1 的并发实验（同 conversation_id 两个 curl &）对容器版再打一遍——这次是跨容器的互斥，Redis 在容器网络里依然一锤定音
  5. Postman 走一遍全链路：/agent/stream 知识库问答（确认 db 迁移过的表都在、pgvector 检索正常）
常见坑 ① 宿主机 8000 端口被本地 uvicorn 占着 → 容器端口映射失败，先停本地服务再 up。
② db 用的是既有数据卷，表都在，无需迁移；若是全新卷（换机器/删卷），用步骤 3 的自动迁移 CMD 或宿主机临时指向容器端口跑一次 alembic upgrade head。
